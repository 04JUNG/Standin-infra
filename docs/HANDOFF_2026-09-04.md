## 2. 확인이 필요한 것 ① — `#49` botocore 버그 (가장 중요)

**Standin-server `#49`(S3에서 Human-Art 모델 번들 프로비저닝)이 기동 시 죽습니다.**

`POSE_MODEL_URI`가 설정되면 `src/pose_model_source.py:89`에서 터집니다.

```
File "src/pose_model_source.py", line 89, in _copy_limited
    set_socket_timeout(max(0.001, min(_REQUEST_TIMEOUT_SECONDS, remaining)))
File "botocore/compat.py", line 70, in set_socket_timeout
    http_response._fp.fp.raw._sock.settimeout(timeout)
AttributeError: 'NoneType' object has no attribute 'raw'
```

직전에 botocore 경고가 함께 찍힙니다 — `Cannot access the socket object of a streaming response.`

- **3KB짜리 `manifest.json`에서 이미 실패합니다.** 큰 ONNX 파일에서 나는 문제가 아닙니다.
- 스테이징에서 ECS circuit breaker가 태스크 정의 `:11`로 롤백했습니다.

### 제안하는 방향

`set_socket_timeout`은 스트리밍 응답에서 하위 소켓 객체를 잡지 못하는 경우가 있습니다.
소켓을 직접 만지는 대신 클라이언트 레벨 타임아웃으로 옮기는 편이 안전합니다.

```python
from botocore.config import Config

client = boto3.client(
    "s3",
    config=Config(connect_timeout=..., read_timeout=..., retries={"max_attempts": ...}),
)
```

전체 예산 관리(`total_budget_seconds`, `_remaining_seconds`)는 지금 구조를 유지하고,
청크 루프에서는 소켓 타임아웃을 다시 걸지 말고 **남은 예산을 넘기면 그냥 끊는** 형태면 됩니다.

### 프로덕션 영향은 없습니다

이중으로 막혀 있습니다.

1. `api/app.py:119-121` — `pose_model_variant`가 `cascade`/`humanart-m`이 아니거나
   `pose_model_uri`가 비어 있으면 즉시 `None`을 돌려줍니다.
2. 프로덕션 인프라는 `poseModelBuildId`가 `""`라 `POSE_MODEL_URI` 자체를 주입하지 않습니다.

그래서 **Standin-server `#51`(승격 PR)은 오늘 머지하지 않았습니다.** main과 develop의 실제
차이는 `#49` 하나뿐이라, 머지해도 프로덕션에서 얻는 기능은 없고 알려진 기동 버그만
main에 올라가면서 추론 재배포가 트리거됩니다. 자세한 내용은 `#51`에 코멘트로 남겨뒀습니다.

> `#51`의 `release/2026-09-04b` 브랜치는 지금 **트리가 main과 같아 빈 PR**입니다.
> `#50`이 머지되며 `#48`까지 이미 main에 들어갔기 때문입니다.
> `#49` 수정 후 브랜치를 현재 develop 트리로 갱신한 뒤 승격해 주세요.

## 3. 확인이 필요한 것 ② — 임시 우회값 되돌리기

**`#49`가 고쳐지면 원래 값으로 되돌려야 합니다.**

## 4. 확인이 필요한 것 ③ — converter 이미지가 아직 로컬 빌드

`standin/converter:latest` (654MB, 태그 `adb5fae9…`)는 **CI가 아니라 제가 로컬에서 빌드해
올린 이미지**입니다. `Deploy converter` 워크플로가 저장소 변수
`CONVERTER_AUTO_DEPLOY_ENABLED=false`로 꺼져 있어 지금까지 두 번 다 건너뛰었습니다.

지금까지는 켤 수 없었습니다 — 워크플로의 배포 단계가 갱신할 **프로덕션 converter ECS
서비스가 없었기** 때문입니다. 오늘 `#42`로 서비스가 생겼으니 이제 교체할 수 있습니다.

### 순서

1. 환경 변수 `CONVERTER_ECS_SERVICE`를 넣습니다. **지금 두 환경 모두 빠져 있습니다**
   (`CONVERTER_ECS_CLUSTER`만 있습니다).

   | 환경 | 값 |
   | --- | --- |
   | `beta` | `StandinApp-ConverterServiceDE3E8133-5scSTQriR9PT` |
   | `staging` | 아래 명령으로 조회 |

   ```bash
   aws ecs list-services --region ap-northeast-2 --cluster StandinStagingApp-ClusterEB0386A7-fTa8F6KCe561
   ```

2. 저장소 변수 `CONVERTER_AUTO_DEPLOY_ENABLED`를 `true`로 바꿉니다.
3. main에서 `Deploy converter`를 `workflow_dispatch`로 돌립니다.

### 현재 이미지를 그대로 둬도 되는 근거

- 기동 시 `converter/SHA256SUMS.v325` 모듈 해시를 검증합니다. 내용이 어긋나면 뜨지 않습니다.
- 스테이징이 같은 이미지로 FBX 내보내기까지 성공했습니다.
- 프로덕션에서 `/healthz` 200으로 정상 기동했습니다.

다만 **재현 가능한 산출물이 아니라는 점**이 문제라 교체를 권합니다.

## 5. FBX 관련 참고

### 타임아웃을 다시 잡았습니다

처음 넣은 `CONVERTER_TIMEOUT_SECONDS=30`은 제가 잘못 잡은 값이었습니다.
CI의 **합성 64KB 캐릭터**로 측정한 3.4초를 기준으로 삼았는데, 실제
`standin-master-v2.fbx`는 **1.72MB**이고 변환에 **18~35초**가 걸립니다.

현재 값 (infra `#36`):

| 위치 | 값 |
| --- | --- |
| Converter | `CONVERTER_TIMEOUT_SECONDS = 60` |
| BFF | `CONVERTER_TIMEOUT_MS = 90000` |

측정치: 변환 중 **CPU 99.5%** (1 vCPU를 다 씁니다), 메모리는 2GB의 13.5%.
CPU가 병목이라 `CONVERTER_MAX_CONCURRENT_PROCESSES = 1`, uvicorn도 `--workers 1`로 묶어뒀습니다.

### 비용

Fargate 1 vCPU / 2GB **상시 1대**가 늘어 **월 $36 정도** 추가됩니다.
유휴일 때도 계속 떠 있는 구조입니다. 쓰지 않을 때 내리고 싶으면 별도로 논의가 필요합니다.

### 플래그가 프로덕션·스테이징 공용입니다

`converterEnabled` / `fbxExportEnabled`는 `cdk.json`에서 **환경별로 나뉘어 있지 않습니다**
(`stagingConverterEnabled` 같은 키가 없습니다). 오늘 `true`로 바꿨으니
**다음 스테이징 배포에서도 그대로 켜집니다.** 스테이징엔 이미 converter가 있어 실질 변화는 없습니다.

## 6. 클라이언트 쪽에 남은 함정 (서버와 무관, 공유만)

릴리스 버전을 **릴리스 브랜치에서만** 올리고 develop은 그대로 두는 방식이라,
다음 승격 PR이 develop 트리를 main에 얹는 순간 **버전이 되돌아갑니다.**

오늘 실제로 그렇게 됐습니다. `#70` 승격 직후 main이 `0.1.1-beta.2`로 돌아간 채
릴리스 빌드가 돌아, 산출물이 `v0.1.1-beta.7`이 아니라 예전 draft `v0.1.1-beta.2`에
올라갔습니다. `#71`로 버전을 올려 다시 빌드해 해결했습니다.

공개 릴리스와 업데이터 피드에는 영향이 없었습니다 — 덮인 건 공개된 적 없는 draft였고,
`releases/latest`는 그동안 `v0.1.1-beta.6`을 가리키고 있었습니다.

develop에도 버전을 함께 올려두면 반복을 막을 수 있습니다. 현재 develop은 `0.1.1-beta.2`입니다.
